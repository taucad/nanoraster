Everything below is imported from `nanoraster`. GLB bytes you pass in are owned by
the call; the bytes you get back are newly allocated and yours.

## Every option and its default

```typescript
import { renderImage } from 'nanoraster';

const image = await renderImage(glb, {
  format: 'webp', // required: 'png' | 'webp' | 'jpeg' | 'jpg' | 'raw'
  width: 768, // default
  height: 432, // default
  quality: 1, // webp default (lossless); jpeg defaults to 0.92; png and raw ignore it
  margin: 0.1, // default
  up: 'y', // default
  projection: 'perspective', // default
  background: undefined, // default (transparent)
  axes: false, // default
  scaleBar: false, // default
  lighting: 'studio', // default
  label: undefined, // default (no label drawn)
  phi: 60, // default
  theta: -45, // default
});
```

`renderImages` takes the same shared keys, minus `phi`, `theta` and `label`,
plus `views: [{ id, label?, phi, theta, width?, height?, format?, quality? }]`:
one entry per image, in result order, where each view may override the shared
output settings. It also accepts `timings: true` to attach stage timings to the
result.

`format: 'raw'` is the fourth output: the encoder is skipped and `bytes` is the
frame itself. It takes every other option unchanged, may be set per view, and
so may sit beside encoded views in one plan call —
[Work with raw pixels](guides/work-with-raw-pixels) covers when that is what you
want.

## Render

### `renderImage`

Render one GLB camera view to one owned output file — encoded, or the raw
frame itself with `format: 'raw'`.

```typescript
export declare const renderImage: (
  glb: Uint8Array<ArrayBuffer>,
  options: RenderImageOptions,
) => Promise<RenderedImageFile>;
```

- **Parameters:** owned GLB bytes and one validated render request.
- **Returns:** a newly allocated `render.<format>` file, carrying the width and
  height the request resolved to.
- **Throws:** `RenderError` for invalid requests, malformed GLB data, GPU faults,
  or encoding failures.

```typescript
import { renderImage } from 'nanoraster';

const image = await renderImage(glb, { format: 'webp', width: 512 });
```

### `renderImages`

Parse and upload a GLB once, then render an ordered set of identified views —
the plan call. Each view may override the shared `width`, `height`, `format`,
and `quality`, so one call renders a whole resolution or format ladder.

```typescript
export declare const renderImages: <const Options extends RenderImagesOptions>(
  glb: Uint8Array<ArrayBuffer>,
  options: StrictRenderImagesOptions<Options>,
) => Promise<RenderedImagesResult<Options>>;
```

[`StrictRenderImagesOptions`](#strictrenderimagesoptions) is the exactness
check: callers pass `RenderImagesOptions`, while TypeScript rejects extra
keys, empty view tuples, and misplaced per-view settings.
[`RenderedImagesResult`](#renderedimagesresult) is the
[`RenderedImages`](#renderedimages) tuple, plus a
[`RenderTimings`](#rendertimings) on its `timings` property when the options
literal set `timings: true`.

- **Parameters:** owned GLB bytes and shared settings with a non-empty view tuple.
- **Returns:** a tuple with the input view IDs and order preserved; each
  entry's MIME type follows its own `format` override when one is set.
- **Throws:** as above, plus a mismatch between the views requested and the
  images the renderer returned.

```typescript
import { renderImages } from 'nanoraster';

const [iso, front] = await renderImages(glb, {
  format: 'webp',
  views: [
    { id: 'iso', phi: 60, theta: -45 },
    { id: 'front', phi: 90, theta: 0 },
  ],
});
```

## Renderer reuse

Every one-shot function above shares one lazily created renderer per process,
so only the first call pays the GPU bring-up and the calls run in sequence.
That renderer uses the default power preference and lives until the process
exits; create your own for a lifetime you control —
[Reuse the renderer](guides/reuse-the-renderer) covers when and how.

### `createRenderer`

Create a renderer that keeps the GPU device, shader, and pipelines alive
across calls.

```typescript
export declare const createRenderer: (options?: CreateRendererOptions) => Promise<Renderer>;
```

- **Parameters:** optional GPU selection hints.
- **Returns:** a [`Renderer`](#renderer) bound to one warm device.
- **Throws:** `RenderError` with code `adapter-unavailable` when no compatible
  adapter exists, or `parse` for invalid options.

```typescript
import { createRenderer } from 'nanoraster';

using renderer = await createRenderer({ powerPreference: 'low-power' });
const image = await renderer.renderImage(glb, { format: 'webp' });
```

### `Renderer`

The persistent handle returned by [`createRenderer`](#createrenderer). Its two
render methods mirror the module-level functions exactly — same options, same
results, byte-identical pixels on the same adapter — but reuse one device.

```typescript
export type Renderer = {
  readonly renderImage: (
    glb: Uint8Array<ArrayBuffer>,
    options: RenderImageOptions,
  ) => Promise<RenderedImageFile>;
  readonly renderImages: <const Options extends RenderImagesOptions>(
    glb: Uint8Array<ArrayBuffer>,
    options: StrictRenderImagesOptions<Options>,
  ) => Promise<RenderedImagesResult<Options>>;
  readonly dispose: () => void;
  readonly [Symbol.dispose]: () => void;
};
```

Contract points:

- A renderer is **single-realm**: create it inside the worker that uses it.
  Handles cannot cross `postMessage`; bytes can.
- Calls on one renderer run **in sequence**; a declared set of images should
  always go through one `renderImages` call, never a loop.
- **Device loss is recovered transparently** on the next call; the renderer
  rebuilds its device and re-uploads on demand.
- After `dispose()`, every call rejects with `RenderError` code `'gpu'` —
  recreate the renderer rather than retrying the call. `dispose` waits for
  in-flight calls to settle, is idempotent, and backs `using` declarations
  through `Symbol.dispose`.

### `describeAdapter`

Describe the adapter a renderer created with these options would bind. Pass
the same `powerPreference` you would pass `createRenderer`, or nothing for the
`'high-performance'` default the one-shot functions use.

```typescript
export declare const describeAdapter: (options?: CreateRendererOptions) => Promise<AdapterInfo>;
```

`deviceType === 'cpu'` means software rasterization (SwiftShader, lavapipe,
WARP): renders work but run an order of magnitude slower. `navigator.gpu`
existing does not rule this out, so use this as the preflight when performance
matters — [Handle render failures](guides/handle-render-failures) shows the
pattern.

Native hosts report the full device class. Browsers report `'unknown'` unless
the adapter is a declared fallback, because WebGPU deliberately withholds it;
a browser with only software support usually hands out no adapter at all, so
`describeAdapter` rejects with `adapter-unavailable` instead of describing one.

## Options held in a variable

Passing an object literal straight to a render call keeps every literal type.
Assigning it to a variable first does not: TypeScript widens `'webp'` to
`string` and the view IDs with it, so the result tuple loses its names. Write
`as const satisfies` on the variable to keep the literals and still have the
keys checked. There is no helper to import and nothing is added to the bundle
— the whole thing is compile-time.

```typescript
import { renderImages, type RenderImagesOptions } from 'nanoraster';

const options = {
  format: 'webp',
  views: [{ id: 'iso', phi: 60, theta: -45 }],
} as const satisfies RenderImagesOptions;

const [iso] = await renderImages(glb, options);
```

`satisfies RenderImageOptions` does the same for the singular call. Both
reject misspelled keys (`includeAxis`), misplaced ones (a per-view `phi` at
call level), and missing required ones, at the property that is wrong.

### `RenderImageView`

```typescript
export type RenderImageView<Id extends string = string> = {
  readonly id: Id;
  readonly label?: string;
  readonly phi: number;
  readonly theta: number;
  readonly width?: number;
  readonly height?: number;
  readonly format?: 'png' | 'webp' | 'jpeg' | 'jpg' | 'raw';
  readonly quality?: number;
};
```

IDs must be unique within a request. The four output fields are per-view
overrides: each defaults to the shared call-level value, follows the same
validation (including the annotated minimum and WebP's
lossless-at-exactly-1 rule), and flows into that entry's filename and MIME
type. `format: 'raw'` is accepted here too, so one plan can return an encoded
thumbnail and an unencoded frame together.

<auto-type-table path="./props.ts" name="RenderImageView" caption="RenderImageView properties" />

### `RenderImagesOptions`

```typescript
export type RenderImagesOptions<Views extends readonly RenderImageView[] = readonly RenderImageView[]> =
  RenderImageSharedOptions & {
    readonly timings?: boolean;
    readonly views: Views;
  };
```

`views` must be a non-empty ordered tuple with unique IDs. A view is labelled
when its own entry sets `label`, so a sheet can label some views and not
others. `timings: true` attaches a [`RenderTimings`](#rendertimings) to the
result without changing what is rendered.

<auto-type-table path="./props.ts" name="RenderImagesOptions" caption="RenderImagesOptions properties" />

### `StrictRenderImagesOptions`

The exact parameter type of [`renderImages`](#renderimages) and
`Renderer.renderImages`: `RenderImagesOptions` narrowed so extra keys, empty
view tuples, and per-view settings placed at call level are compile errors.
`NoExtraKeys`, `StrictViews`, and `StrictLighting` are the internal
compile-time checks behind it, with no runtime form.

Callers write plain `RenderImagesOptions` object literals and never name this
type — reach for it only to forward the plan call through your own generic
wrapper, where the parameter type has to be spelled out:

```typescript
import { renderImages, type RenderImagesOptions, type StrictRenderImagesOptions } from 'nanoraster';

const renderCatalogue = async <const Options extends RenderImagesOptions>(
  glb: Uint8Array<ArrayBuffer>,
  options: StrictRenderImagesOptions<Options>,
) => renderImages(glb, options);
```

### `RenderLighting`

```typescript
export type RenderLighting = 'studio' | RenderLightingRig;
```

The studio preset by name, or a rig. Omitting `lighting`, passing `'studio'`
and spelling out the studio values render the same bytes; one rig applies to a
singular render and to every view of a batch. [Light the subject](guides/light-the-subject)
shows each field in use.

### `RenderLightingRig`

A rig replaces the studio lights outright and inherits every other studio
value it leaves out. Directions are view-space by default (`+x` right, `+y` up,
`+z` toward the viewer); `space: 'world'` authors them in glTF coordinates.

## Results

### `RenderedImageFile`

Returned directly by [`renderImage`](#renderimage), and on the `file` of every
batch entry. `width` and `height` are the shape the request resolved to, so a
result needs no second lookup to be read, diffed, or uploaded.

With `format: 'raw'`, `bytes` is the frame rather than an encoded file:
straight-alpha, sRGB-encoded RGBA8, exactly `width * height * 4` bytes,
row-major with the top row first, four bytes per pixel and no padding — the
layout a canvas `ImageData` expects after a `Uint8ClampedArray` wrap, and
`mimeType` is `application/octet-stream`. Neighbouring libraries make other
choices, so [Work with raw pixels](guides/work-with-raw-pixels) sets this
layout against them.

<auto-type-table path="./props.ts" name="RenderedImageFile" caption="RenderedImageFile properties" />

```typescript
import { renderImage } from 'nanoraster';

import { writeFile } from 'node:fs/promises';

const image = await renderImage(glb, { format: 'webp' });
await writeFile(image.name, image.bytes);
```

### `RenderedImages`

The ordered tuple inside every plan-call result.

```typescript
export type RenderedImages<
  Views extends readonly RenderImageView[],
  SharedFormat extends ImageFormat = ImageFormat,
> = {
  readonly [Index in keyof Views]: Views[Index] extends RenderImageView<infer Id>
    ? RenderedImage<Id, ViewOutputFormat<Views[Index], SharedFormat>>
    : never;
};
```

This mapped tuple preserves each input view's literal ID, position, and tuple
length, and narrows each entry's MIME type through its view's `format`
override (falling back to the shared format). It does not expose `Array`
prototype members as result fields. `ViewOutputFormat` is the internal
conditional that picks the override when one exists.

```typescript
import { renderImages } from 'nanoraster';

const [iso, top] = await renderImages(glb, {
  format: 'webp',
  views: [
    { id: 'iso', phi: 60, theta: -45 },
    { id: 'top', phi: 0, theta: 0 },
  ],
});

console.log(iso.id, iso.file.name); // 'iso' 'render-iso.webp'
console.log(top.id, top.file.name); // 'top' 'render-top.webp'
```

### `RenderedImagesResult`

What [`renderImages`](#renderimages) and `Renderer.renderImages` actually
resolve to: the [`RenderedImages`](#renderedimages) tuple, and — only when the
options literal set `timings: true` — a [`RenderTimings`](#rendertimings) on
its `timings` property. Reading `timings` without having asked for it is a
compile error, so the flag and the field cannot drift apart.

```typescript
import { renderImages, type RenderedImagesResult, type RenderImagesOptions } from 'nanoraster';

const options = {
  format: 'webp',
  timings: true,
  views: [{ id: 'iso', phi: 60, theta: -45 }],
} as const satisfies RenderImagesOptions;

const result: RenderedImagesResult<typeof options> = await renderImages(glb, options);
console.log(result[0].file.name, result.timings.parse); // 'render-iso.webp' 0.42
```

### `RenderTimings`

Attached to a plan call's result when the options set `timings: true`. The
fields map onto the pipeline stages [How it works](how-it-works) documents:
parse, setup (device acquisition plus geometry upload), then per-view
rasterise and encode. Every duration is milliseconds on the host's clock.

## Errors

Rendering rejects with `RenderError`. Parse and encode failures are
deterministic for the same request; GPU faults may succeed after the host or
device recovers, which
[Handle render failures](guides/handle-render-failures) turns into a retry
policy.

### `RenderFailureCode`

```typescript
export type RenderFailureCode =
  | 'adapter-unavailable'
  | 'device-lost'
  | 'gpu'
  | 'parse'
  | 'encode'
  | 'unknown';
```

| Value                 | Meaning                                                     | Retry guidance                                              |
| --------------------- | ----------------------------------------------------------- | ----------------------------------------------------------- |
| `adapter-unavailable` | No compatible GPU adapter was available.                    | Keep the last image and retry after host recovery.          |
| `device-lost`         | The GPU device was lost during rendering.                   | Keep the last image and retry with a new device.            |
| `gpu`                 | Another adapter, driver, or render-pass failure occurred.   | Treat as transient unless host diagnostics prove otherwise. |
| `parse`               | GLB bytes or request options violated the input contract.   | Fix the input before retrying.                              |
| `encode`              | The selected encoder could not produce the requested image. | Fix the format or background before retrying.               |
| `unknown`             | The thrown value had no recognised failure tag.             | Inspect `message` and preserve the original context.        |

### `RenderError`

`RenderError` extends the native `Error` class and adds this public surface:

```typescript
export declare class RenderError extends Error {
  readonly code: RenderFailureCode;
  constructor(code: RenderFailureCode, message: string);
  static from(error: unknown): RenderError;
  get isGpuFault(): boolean;
}
```

- `constructor(code, message)` creates an explicitly classified error.
- `RenderError.from(error)` returns an existing `RenderError` unchanged or
  classifies any other thrown value; it never throws.
- `code` is the stable machine-readable classification.
- `isGpuFault` is `true` for `adapter-unavailable`, `device-lost`, and `gpu`.

```typescript
import { RenderError, renderImage } from 'nanoraster';

try {
  await renderImage(glb, { format: 'webp' });
} catch (error) {
  const failure = RenderError.from(error);
  if (!failure.isGpuFault) throw failure;
}
```

## Constants

Every exported bound and pattern the validator applies. Ranges are inclusive and
the regular expressions are the exact runtime values. Import them rather than
restating them, so caller-side checks cannot drift.

| Export                             | Runtime value                             | Unit or syntax              | Affected field              |
| ---------------------------------- | ----------------------------------------- | --------------------------- | --------------------------- |
| `renderImageDimensionRange`        | `readonly [16, 4096]`                     | pixels                      | `width`, `height`           |
| `renderImageQualityRange`          | `readonly [0, 1]`                         | normalised encoder quality  | `quality`                   |
| `renderImageMarginRange`           | `readonly [0, 0.5]`                       | fraction of fitted extent   | `margin`                    |
| `renderImageAnnotatedMinDimension` | `192`                                     | pixels                      | annotated `width`, `height` |
| `renderImageLabelMaxLength`        | `64`                                      | Unicode code points         | `label`                     |
| `renderImageLabelPattern`          | `/^[\u0020-\u007E\u00B5\u2014\u2212]+$/u` | supported characters        | `label`                     |
| `renderImageViewIdPattern`         | `/^[\dA-Za-z][\w-]{0,63}$/u`              | identifier syntax           | `id`                        |
| `renderImageBackgroundPattern`     | `/^#[\dA-Fa-f]{6}(?:[\dA-Fa-f]{2})?$/u`   | hexadecimal colour          | `background`                |
| `renderImageMaxLights`             | `8`                                       | lights per rig              | `lighting.lights`           |
| `renderImageLightColorRange`       | `readonly [0, 32]`                        | linear radiance per channel | `lighting.lights[].color`   |
| `renderImageAmbientRange`          | `readonly [0, 4]`                         | diffuse multiplier          | `lighting.ambient`          |
| `renderImageExposureRange`         | `readonly [0.01, 16]`                     | linear multiplier           | `lighting.exposure`         |

```typescript
import { renderImageDimensionRange } from 'nanoraster';

const [min, max] = renderImageDimensionRange;

const clamp = (value: number): number => Math.min(Math.max(value, min), max);
```

### `renderImageDimensionRange`

Inclusive pixel bounds for both image dimensions.

### `renderImageMarginRange`

Inclusive corner-fit margin bounds.

### `renderImageAnnotatedMinDimension`

Minimum width and height when any annotation is enabled.

### `renderImageQualityRange`

Inclusive encoder-quality bounds. JPEG treats the value as compression level
(default `0.92`). WebP treats `1` — its default — as lossless and anything
lower as lossy, matching Chrome's canvas `toBlob` semantics. PNG and raw
ignore it.

### `renderImageBackgroundPattern`

Hex clear-colour syntax. Backgrounds may also be supplied as normalised
straight-alpha RGBA, which this pattern does not cover.

### `renderImageLabelMaxLength`

Maximum label length in Unicode code points.

### `renderImageLabelPattern`

Supported label characters: printable ASCII plus the micro sign, em dash, and
minus sign.

### `renderImageViewIdPattern`

Stable view identifier syntax. IDs become result filenames, which is why the
first character is restricted.

### `renderImageMaxLights`

Most directional lights one rig may carry.

### `renderImageLightColorRange`

Inclusive per-channel bounds for a light's linear radiance.

### `renderImageAmbientRange`

Inclusive bounds for the rig's flat ambient multiplier.

### `renderImageExposureRange`

Inclusive bounds for the pre-tone-map exposure multiplier.
