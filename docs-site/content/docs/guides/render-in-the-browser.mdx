---
title: Render in the browser
description: Run nanoraster on browser WebGPU, bundle the WebAssembly artifact, and degrade gracefully where WebGPU is missing.
---

Render in a browser tab on WebGPU, using the API and render core that the
Node.js build uses.

You need WebGPU enabled and a bundler that can emit a WebAssembly asset. Vite,
webpack 5 and Rspack all do without configuration; [Install](../install)
covers how the artifact is delivered.

### 1. Check for a WebGPU adapter first

Rendering fails with a typed error when no adapter exists; checking first lets
you choose a fallback before doing any work.

```typescript
const supported = typeof navigator !== 'undefined' && 'gpu' in navigator;

if (!supported) {
  throw new Error('This browser has no WebGPU support.');
}
```

`navigator.gpu` is necessary but not sufficient: a browser can expose the API
and still fail to produce an adapter on a particular machine. Handle
[`adapter-unavailable`](handle-render-failures) too.

### 2. Render from bytes you already hold

Only the source of the GLB differs: a fetch, a file input or an in-memory
buffer instead of the filesystem.

```typescript
import { renderGlbToImage } from 'nanoraster';

const response = await fetch('/model.glb');
const glb = new Uint8Array(await response.arrayBuffer());

const image = await renderGlbToImage(glb, {
  format: 'webp',
  width: 640,
  height: 480,
});
```

### 3. Show or download the result

The result is raw bytes, so wrap it in a `Blob` to display it.

```typescript
const blob = new Blob([image.bytes], { type: image.mimeType });
const url = URL.createObjectURL(blob);

document.querySelector('img')?.setAttribute('src', url);
```

Revoke it with `URL.revokeObjectURL(url)` once the image has loaded, or the blob
stays resident for the life of the document.

### 4. Keep the render off the main thread

Rendering occupies the GPU queue and spends CPU time encoding the result. In
a worker, neither blocks input handling.

```typescript
// render.worker.ts
import { renderGlbToImage } from 'nanoraster';

self.addEventListener('message', async ({ data }: MessageEvent<Uint8Array>) => {
  const image = await renderGlbToImage(data, { format: 'webp' });
  self.postMessage(image.bytes, [image.bytes.buffer]);
});
```

Transferring `image.bytes.buffer` moves the memory instead of copying it; the
worker cannot use it afterwards, and does not need to.

## Variations

**Cross-origin isolation.** The browser build does not require
`SharedArrayBuffer`, so COOP/COEP headers are not needed.

**Node and browser from one codebase.** The import specifier is the same in
both, and nothing in your code needs to branch.

**Capturing a live viewer's camera.** An orbiting viewer (three.js, Babylon,
your own) knows its eye position relative to the target; nanoraster wants
`phi` and `theta`. Convert the offset; for a Y-up scene:

```typescript
const anglesFromOffset = ([x, y, z]: readonly [number, number, number]) => {
  const distance = Math.hypot(x, y, z);
  const degrees = 180 / Math.PI;
  return {
    phi: Math.acos(y / distance) * degrees,
    theta: Math.atan2(-z, x) * degrees,
  };
};

const image = await renderGlbToImage(glb, { format: 'webp', ...anglesFromOffset(eye) });
```

Distance is discarded on purpose: nanoraster
[fits the model itself](frame-the-model), so the capture matches the viewer's
direction, not its zoom.
