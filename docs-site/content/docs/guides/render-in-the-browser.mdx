title: Render in the browser
description: Run nanoraster on browser WebGPU, bundle the WebAssembly artifact, and degrade gracefully where WebGPU is missing.

Render in a browser tab on WebGPU, using the API and render core that the
Node.js build uses.

You need WebGPU enabled and a bundler that can emit a WebAssembly asset. Vite,
webpack 5 and Rspack all do without configuration; [Install](../install)
covers how the artifact is delivered.

### 1. Check for a WebGPU adapter first

Rendering fails with a typed error when no adapter exists; checking first lets
you choose a fallback before doing any work.

```typescript
const supported = typeof navigator !== 'undefined' && 'gpu' in navigator;

if (!supported) {
  throw new Error('This browser has no WebGPU support.');
}
```

`navigator.gpu` is necessary but not sufficient: a browser can expose the API
and still fail to produce an adapter on a particular machine — or hand you a
software one. `describeAdapter()` names what you actually got, reading
`navigator.gpu` directly, so the check costs no wasm download. A `'cpu'`
device type means SwiftShader-class rasterization, roughly an order of
magnitude slower. Handle [`adapter-unavailable`](handle-render-failures) too.

```typescript
import { describeAdapter } from 'nanoraster';

const adapter = await describeAdapter();
if (adapter.deviceType === 'cpu') {
  console.warn(`software rasterizer: ${adapter.name}`);
}
```

Browsers report `deviceType: 'unknown'` unless the adapter declares itself a
fallback — the WebGPU specification withholds the class deliberately. The
`name` is what the browser discloses: `"google swiftshader"` in headless
Chrome, `"apple"` in Safari, `""` in Firefox.

### 2. Render from bytes you already hold

Only the source of the GLB differs: a fetch, a file input or an in-memory
buffer instead of the filesystem.

```typescript
import { renderImage } from 'nanoraster';

const response = await fetch('/model.glb');
const glb = new Uint8Array(await response.arrayBuffer());

const image = await renderImage(glb, {
  format: 'webp',
  width: 640,
  height: 480,
});
```

### 3. Show or download the result

The result is raw bytes, so wrap it in a `Blob` to display it.

```typescript
const blob = new Blob([image.bytes], { type: image.mimeType });
const url = URL.createObjectURL(blob);

document.querySelector('img')?.setAttribute('src', url);
```

Revoke it with `URL.revokeObjectURL(url)` once the image has loaded, or the blob
stays resident for the life of the document.

### 4. Keep the render off the main thread

Rendering occupies the GPU queue and spends CPU time encoding the result. In
a worker, neither blocks input handling. Create the renderer once when the
worker starts and dispose it when the worker closes — one renderer per worker,
its whole life.

```typescript
// render.worker.ts
import { createRenderer, type Renderer } from 'nanoraster';

let renderer: Promise<Renderer> | undefined;

self.addEventListener('message', async ({ data }: MessageEvent<Uint8Array>) => {
  try {
    renderer ??= createRenderer();
    const image = await (await renderer).renderImage(data, { format: 'webp' });
    self.postMessage(image.bytes, [image.bytes.buffer]);
  } catch (error) {
    self.postMessage({ error: error instanceof Error ? error.message : String(error) });
  }
});

self.addEventListener('close', () => {
  void renderer?.then((handle) => {
    handle.dispose();
  });
});
```

A renderer is single-realm: bytes cross `postMessage`, handles never do, so
the worker owns the renderer and posts results out. Transferring
`image.bytes.buffer` moves the memory instead of copying it; the worker cannot
use it afterwards, and does not need to.

The catch matters: a rejection inside the listener would otherwise vanish as
an unhandled rejection and the caller would wait forever, so a failure is
posted back as its own message shape — bytes mean success, `{ error }` means
the render failed. [Handle render failures](handle-render-failures) covers
classifying the error, and [Reuse the renderer](reuse-the-renderer) covers the
lifetime in depth. On the main thread the one-shot functions still work — the
price is readback and encode competing with input handling, and a GPU device
that stays alive after the render, because the shared renderer is never
disposed.

## Variations

**Cross-origin isolation.** The browser build does not require
`SharedArrayBuffer`, so COOP/COEP headers are not needed.

**Node and browser from one codebase.** The import specifier is the same in
both, and nothing in your code needs to branch.

**Capturing a live viewer's camera.** An orbiting viewer (three.js, Babylon,
your own) knows its eye position relative to the target; nanoraster wants
`phi` and `theta`. Convert the offset; for a Y-up scene:

```typescript
const anglesFromOffset = ([x, y, z]: readonly [number, number, number]) => {
  const distance = Math.hypot(x, y, z);
  const degrees = 180 / Math.PI;
  return {
    phi: Math.acos(y / distance) * degrees,
    theta: Math.atan2(-z, x) * degrees,
  };
};

const image = await renderImage(glb, { format: 'webp', ...anglesFromOffset(eye) });
```

Distance is discarded on purpose: nanoraster
[fits the model itself](frame-the-model), so the capture matches the viewer's
direction, not its zoom.
